# gotzji release process

This is the canonical release sequence for the owned Windows x64 fork. Historical cross-platform lnwjud releases are recorded under docs/upstream/ and are not gotzji qualification.

1. Implement on dev, preserve peer files and original lnwjud state, and run focused plus full affected checks. Review standards, the accepted specification and the end-to-end source paths with scrutinize.
2. Complete product operations before changing the source version. Use the canonical set-version script, test:version and verify-release.ps1 -SkipWindowsPackaging; never turn a source version into a published-version claim.
3. Commit only explicit owned source paths, push dev, and merge the verified dev -> main PR through the owned repository's protection process. Record exact main SHA and exact CI run. A failed or non-terminal run cannot qualify a release.
4. Build a private Windows x64 candidate once from the clean accepted commit. Verify both installer and portable bytes, complete runtime manifest, MIT/third-party redistribution notices and official-unsigned trust policy. NotSigned is intentional; automatic updates stay disabled.
5. Complete every G01-G20 sub-gate applicable before publication in .github/RELEASE_CHECKLIST.md, including actual Grace/Plus/Pro/native work, exact installed recovery, fresh-owner/machine, migration/rollback and normal-use pilot. Store private evidence outside the public source. Each record identifies the candidate build/catalog/source and actual scenario. Synthetic/component results never stand in for runtime acceptance.
6. Keep the candidate immutable. Any source/runtime/catalog change invalidates affected candidate evidence and requires a replacement candidate. Evidence-only additions must not change its runtime bytes.
7. Tag the exact accepted main commit only after the pre-publication gates pass. Publish the same qualified installer/portable/plugin assets and checksums/notices/instructions from the owner-controlled channel. Do not rebuild during publication or consume an upstream artifact/feed.
8. Independently download the released files, compare hashes, install/launch and invoke the personal plugin. G20 completes only after those observed checks. Do not claim official v1.0.0 or 100% until all mandatory criteria are current PASS.

Public ChatGPT directory submission is separate from the personal tunnel-connected plugin. A tunnel ID, reachable host, source push, passing CI or an installer filename is not full-release acceptance. Owner-only credentials, Windows restart, unavailable Plus accounts and additional-machine tests remain explicit prerequisites; continue independent work without inventing evidence.

The public plugin asset is the generic `gotzji-plugin-<version>-unbound.zip` plus its external checksum and `PLUGIN_PROVENANCE.json`. It contains `app-binding.template.json`, never `.app.json`, a registered technical app ID, tunnel credentials or an owner mapping. The owner creates a separate local personal package only after ChatGPT issues the registered MCP technical ID. A valid template package proves file inventory and provenance only; G14/G15 still require observed Pro and Plus connection, consent, tool invocation, same-job control and reconnect records.

Canonical sequence: dev -> PR -> main CI -> tag -> Release -> dev sync.
Never create or push the release tag before reviewed candidate acceptance and successful exact `main` SHA CI. The artifact is windows-release-<main merge SHA>. The source-only verifier uses -SkipWindowsPackaging. Synchronize branches after release.

Use scripts/release-notes.mjs for exact-version human-written Highlights followed by nonempty ## Features, ## Bug Fixes, ## Other Changes and **Full Changelog** where supported by actual changes. Publish a sanitized QUALIFICATION.json to the private draft candidate-<version>; it declares the reviewed G01-G19 acceptance of exact source/runtime/artifact hashes and excludes raw personal/provider logs. The tag workflow validates that declaration before aggregating the original Windows bytes with --windows-only. Declaration validation is not an automatic performance/account proof; reviewers must inspect the retained private scenario receipts. G20 remains post-publication acceptance.
